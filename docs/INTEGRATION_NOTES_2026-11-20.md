## 문제 1: 두 검색에 나왔다는 이유로 높은 순위를 받아도 되는가

사용자는 “고양이 사진은 이미지 검색에만 정확히 나오는데, 무관한 PDF가 본문·이미지 양쪽에 나와 더 높아지면 잘못된 것 아닌가”와 “본문만 정확한 문서가 불리해지지 않는가”를 질문했습니다. 검색 경로 수가 관련성의 증거가 되는지 검토할 필요가 있었습니다.

| 단계 | 시도·판단 | 현재 상태 |
|---|---|---|
| 원본 점수 확인 → 낮은 관련성 필터 → RRF | 본문·이미지 순위를 합쳤지만 두 목록에 모두 등장한 파일이 가산되는 문제가 사용자 목표와 맞지 않았습니다. RRF는 원본 코사인 점수의 단순 합과는 다르지만 여러 검색 경로에서 순위 기여를 받습니다. | 제거 |
| 검색 경로별 최고 점수 선택 | 두 경로 가산을 없앴습니다. 당시 본문 0.4·이미지 0.2 하한을 두고 기준 초과 비율 (점수-하한)/(1-하한)의 최댓값으로 정렬했습니다. | 이후 제거 |
| 본문 모델·하한 비교 | OpenCLIP 본문을 ko-sroberta로 분리했고 하한 조합 9개를 검토했습니다. 낮은 하한은 누락을 줄여도 무관한 결과의 높은 순위까지 해결하지 못했습니다. | 본문 모델 분리 유지, 하한 제거 |
| 하한 제거 + 재정렬 모델 | 사용자 선택으로 Qwen3-VL-Reranker-2B를 준비해 소규모·일부 실제 질의를 확인했습니다. CPU 지연과 약 4.27GB 용량을 확인한 뒤 사용자가 삭제를 결정했습니다. | 모델·앱 연결 제거, 일부 실행을 최종 성능 근거로 사용하지 않음 |
| 파일 종류에 따른 원본 점수 최댓값 | 사용자 최종 결정: 일반 이미지는 이미지 점수만, PDF/PPTX는 본문·내부 이미지 중 높은 점수로 정렬합니다. | 현재 구현 |

현재 파일별 점수는 다음과 같습니다. 본문은 파일의 모든 본문 청크 중 최고 점수이고, 이미지는 해당 파일의 모든 추출 그림 중 최고 점수입니다.

```text
일반 이미지: image_score
PDF/PPTX: max(document_score, image_score)
한쪽만 추출된 문서: 존재하는 쪽의 점수
최종 정렬: 선택 점수 내림차순
```

예를 들어 사진의 이미지 점수가 0.65이고 PDF가 본문 0.40·이미지 0.30이면 사진이 앞섭니다. 정확한 본문 문서가 0.80이고 다른 문서가 본문 0.55·이미지 0.50이면 정확한 본문 문서가 앞섭니다. 이 숫자는 규칙 설명용 가상 예시입니다.

점수는 정규화 벡터의 내적으로 계산한 코사인 유사도입니다. **벡터의 L2 정규화는 유지하며, 검색 경로 점수의 기준 초과 비율 보정은 제거했습니다.** 두 의미의 “정규화”를 혼동하지 않아야 합니다. 앱은 하한·합산·RRF·재정렬을 사용하지 않으며 0·음수도 반환합니다. 파일명은 모델 입력에서 제외합니다.

남은 고민은 두 모델 점수의 척도입니다. ko-sroberta의 0.6과 OpenCLIP의 0.6이 같은 관련성 확률이라는 뜻은 아닙니다. 가산을 없애면 경로 중복 이점은 사라지지만, 낮은 관련성의 본문 점수가 이미지 점수보다 높아지는 문제는 여전히 가능합니다. 이번 구현의 단순성과 검색 품질을 별도로 평가해야 합니다. 이후 개선을 검토한다면 새 정답·오답 자료로 비교해야 하며, 하한이나 무거운 모델을 최선이라고 단정하지 않습니다.

## 문제 2: 이미지 인코더만 보이는데 본문 검색은 어디에서 되는가

본문은 이미 로더에서 추출되고 있었습니다. 별도 TXT 파일이 생성되지 않고, DocumentEncoder가 내부 그림만 처리하므로 파일 이름만 보면 본문 구현이 없는 것처럼 보일 수 있었습니다.

```text
PDF 텍스트 계층: pypdf page.extract_text()
PPTX 글상자·표: python-pptx paragraph.text / cell.text
    → DocumentChunk.text (메모리)
    → DocumentTextPreparer.prepare()로 긴 본문 분할
    → SentenceDocumentEmbedder (ko-sroberta, 768차원)
    → 본문 FAISS 인덱스

일반 사진·PDF/PPTX 내부 그림
    → 공통 ImageEncoder (OpenCLIP, 512차원)
    → 이미지 FAISS 인덱스
```

문서 그림은 DocumentEncoder가 공통 ImageEncoder로 전달합니다. query_encoder/text_encoder.py의 KoreanTextEncoder는 현재 **이미지 검색어**용 OpenCLIP입니다. 본문 검색어는 SentenceDocumentEmbedder.encode_query()가 ko-sroberta로 인코딩합니다. 원본 OpenCLIP DocumentEmbedder 클래스 파일은 남아 있지만 앱은 이를 직접 생성하지 않습니다.

| 실제 파일 | 로더에서 확인한 내용 | 해석 |
|---|---|---|
| 동적계획법.pdf | 본문 34청크·10,736자·내부 이미지 59개 | OCR 없이 본문·그림 양쪽 검색 가능 |
| 페르소나_경로맵.pptx | 본문 3청크·1,997자·내부 이미지 4개 | 본문이 없는 문서가 아니었음 |
| 로지스틱회귀.pdf | 본문 0개·이미지 23개 | 현재 이미지 검색만 가능, 그림 속 글의 OCR 검색은 불가 |

여기서 청크 수는 긴 본문을 재분할하기 전 로더 출력입니다. 본문 추출 지원과 TXT 파일 지원은 다릅니다. 현재 수집 형식은 PDF/PPTX/JPG/JPEG/PNG/WEBP이며 TXT/MD/DOCX/HWP·구형 PPT는 미지원입니다. 지원 확장자는 db_info.py가 아니라 DocumentScanner의 상수에 있습니다.

OCR 없이도 PDF 텍스트 계층과 PPTX 실제 글은 읽을 수 있습니다. 반면 스캔 글자·도표 속 글은 현재 본문으로 추출하지 못합니다. 문서 페이지 전체를 이미지로 렌더링하는 기능도 없습니다.

## 문제 3: 페르소나 검색 실패와 128토큰 제한

페르소나 PPTX에는 실제 글이 있었지만, 기존 3페이지의 길이는 324/199/356토큰으로 ko-sroberta의 128토큰 설정을 넘었습니다. 당시 최고 본문 점수 약 0.386은 하한 0.4 아래였고, 다른 문서는 약 0.49로 앞섰습니다. 본문 부재·길이 잘림·점수 기준을 나눠 살펴봐야 했습니다.

현재는 모델 길이에서 특수 토큰 2개를 뺀 126토큰 단위로, 32토큰을 겹쳐 긴 본문을 분할합니다. prepare()는 토큰화 단계의 자동 잘림을 끄고 전체 토큰을 나눠 원래 파일·페이지와 연결합니다. 128은 “문서 전체에서 128토큰만 읽는다”는 최종 수집 제한이 아니라 한 번의 모델 입력 길이입니다. 긴 검색어 자체를 여러 조각으로 나눠 검색하는 기능은 이번에 추가하지 않았습니다.

중간에는 문서 파일명을 별도 청크로 넣어 페르소나 주제 질의가 1위가 됐지만, 이는 본문만으로 1위를 얻은 결과와 다릅니다. 사용자가 파일명 검색을 제외하기로 했으므로 현재는 파일명 청크 생성이 없고 오래된 filename 청크도 검색에서 제외합니다. 최종 성능은 파일명 없는 상태로 다시 기록했습니다.

encode_with_crops()는 이미지 한 장을 여러 영역 벡터로 만드는 도구이며 본문 추출이나 OCR 기능이 아닙니다. 함수·메타데이터 대응 테스트는 있지만 현재 앱 분석에서는 호출하지 않습니다. 문서에 여러 그림이 있어 벡터가 여러 개인 경우와 사진을 crop으로 여러 벡터로 만든 경우도 구분했습니다.

최종 구조 정리 후 회귀 테스트 80개 통과(11.268초). 실제 38개 파일·16개 질의 전체 모델 실행은 구조 정리 직전에 수행했고, 문서 정리 때문에 다시 실행하지 않았습니다. 고정된 소규모 자료의 결과이며 독립적인 일반 정확도 평가는 아닙니다. 일부 질의에서는 파일명 제거와 점수 정책을 함께 바꿨으므로 순위 차이를 한 요인의 효과로 단정하지 않습니다. 전체 순위와 비교 조건은 [현재 검색 동작](SEARCH_BEHAVIOR.md)에 있습니다.

## 연구일지에 옮길 활동 요약

이번 주 팀원들이 수정한 로더·임베딩·DB·FAISS를 v3에서 통합하고, 본문 검색과 이미지 검색의 실제 호출 경로를 확인했다. 통합검색에서 두 경로에 등장한 문서가 가산되는 문제를 질문했고, 한 경로에서만 정확한 사진이나 문서가 불리하지 않도록 파일별 최고 점수를 선택하기로 했다. 하한과 점수 보정, 재정렬 모델도 검토했지만 하한만으로 순위 문제를 해결할 수 없었고 무거운 재정렬 모델은 로컬 실행 비용 때문에 제거하기로 했다.

또한 PDF/PPTX의 글이 OCR 없이 추출된다는 점과, 이미지 인코더가 문서의 그림만 담당한다는 점을 구분했다. 페르소나 문서 실패를 조사하며 본문이 없어서가 아니라 긴 입력의 잘림과 점수·검색 기준 문제도 있음을 확인했다. 긴 본문 분할은 유지하되 파일명 검색은 제외하기로 했다. 구현·자동 테스트·실모델 비교는 AI가 수행했으며, 나는 검색 규칙과 기능 범위를 질문하고 최종 방식을 결정했다.

현재 고양이 사진과 핵심 본문 질의는 1위를 확인했지만, 일부 이미지와 페르소나 질의가 밀리는 문제가 남았다. 두 모델의 코사인 점수를 직접 비교하는 방식의 한계를 기록했고, 테스트 통과와 검색 정확도 향상을 같은 의미로 보지 않기로 했다. GUI 세 모드로 비교할 수 있게 하고 샘플·문서를 정리했다. 앞으로는 추가 정답·오답 샘플과 사용자 직접 검색 결과로 개선 방향을 판단할 필요가 있다.


## 팀원 파일 원본 복원 — 2026-11-20 최종 반영

사용자 요청으로 팀원 파일 5개(database/faiss.py, file_encoder/document_encoder.py, file_loader/document_loader.py, query_encoder/text_encoder.py, similarity/document_embedder.py)를 원본 PR #27 병합 직전 160f055와 동일하게 복원했습니다. 팀원 담당 디렉터리에 AI가 추가한 본문 어댑터도 남기지 않도록 connection/sentence_document_embedder.py로 옮겼습니다. 긴 본문 분할은 connection/text_preparation.py에 유지합니다.

본문 ko-sroberta와 이미지 OpenCLIP 분리는 연결 모듈에서 유지하며 app.py가 FAISS 차원을 명시합니다. 원본 FAISS의 기본 본문 차원은 512지만 앱은 본문용 768을 전달합니다. 원본 FAISS는 chunk_type을 메타데이터로 저장하지 않으므로 과거 filename 메타데이터 보호 조건은 키가 있을 때만 동작합니다. 현재 앱은 메모리 인덱스를 새로 만들고 파일명을 인코딩하지 않습니다.

이 복원 이후 테스트 결과는 ACTIVITY_LOG에 추가합니다. 이전 실모델 수치는 복원 전 실행의 기록이며 새 실행 결과로 표현하지 않습니다. 앞서 서술된 팀원 파일 수정은 작업 과정의 이력이고 최종 차이에서는 제거합니다. 현재 원본 파일과 연결 코드의 구분은 이 절을 기준으로 합니다.
